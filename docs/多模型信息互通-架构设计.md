# 多模型信息互通架构设计

> 版本：v1（2026-11-05）
> 前置文档：`docs/多模型调用-待开发清单.md`（P0/P1 已完成：连接 tab 配置 UI + sendRequest 核心函数）
> 本文档解决的问题：**三条模型线路如何共享同一个世界状态、互相喂信息，而不是三条互不相通的独立线路。**

---

## 一、用户需求（明确后的最终版）

> 「API 是 API，信息是要互通的，不是三个独立的线路。对话不知道主事件记录、不知道 NPC 发言，不是我想要的。」

拆成三个角色 + 一个共享状态：

| 角色 | 用什么模型 | 职责 |
|---|---|---|
| **主对话** | 1 个 API（如 pro） | ST 正常聊天，是世界的「叙事主体」 |
| **主事件记录** | 轻量模型（如 flash） | 把剧情进展总结成结构化事件/脉络，供主对话与 NPC 参考 |
| **NPC 发言** | 另一个 API | 判定 NPC 意图 + 生成 NPC 主动发言 |

三者**共享同一个「世界状态 + 事件记录」**，互相能看到对方的产出。

---

## 二、核心技术约束（已对照 ST 1.19.0 源码实锤）

### 2.1 两个 LLM 调用函数的本质区别

| | `generateQuietPrompt` | `ConnectionManagerRequestService.sendRequest` |
|---|---|---|
| 能否指定 profile/模型 | ❌ 无 profile 参数，固定「当前连接」 | ✅ `sendRequest(profileId, ...)` |
| 是否带聊天上下文 | ✅ 走 `Generate('quiet')`，带完整上下文 | ❌ 裸请求，只发传入的 prompt |
| 依赖连接状态 | ✅ 依赖「当前连接」 | ❌ 不依赖，读 profile 字段直发 |
| 并发 | ❌ 全局单连接，会串 | ✅ 可并发 |

**结论**：要实现「多模型 + 信息互通」，唯一正确做法是——

> **用 `sendRequest(profileId)` 指定模型，同时手动把「世界状态 + 主对话上下文」拼进 prompt 喂给它。**

### 2.2 可用的上下文来源（`context` 已导出，前端可直接取）

- `context.chat`：聊天消息对象（`{mesId: {name, mes, ...}}`）
- `context.chatMetadata`：聊天元数据
- `context.name1` / `context.name2`：玩家名 / 角色名
- `context.characters`：角色卡
- `context.getWorldInfoPrompt()`：世界书 prompt
- 后端 `GET /summary` → `buildSummary(state)`：确定性状态摘要（时间/金钱/背包/好感）

### 2.3 信息互通的「两个方向」

1. **辅助模型 → 主对话**：已有机制 `setExtensionPrompt`（`applyInjection`），把状态/事件记录注入主对话 prompt。✅ 已就绪，只需扩充注入内容。
2. **主对话 → 辅助模型**：需要**手动取 `context.chat` 最近消息**，拼进发给辅助模型的 prompt。❌ 待实现。

## 三、目标架构

```
                          ┌──────────────────────────┐
                          │      世界状态 (state)     │
                          │  events / narrative /     │
                          │  intent / encounterLog    │
                          └──────────────────────────┘
                               ▲  ▲  ▲         │  │
                write back     │  │  │         │  │ inject(已就绪)
        ┌──────────────────────┘  │  └─────────┼──┼──────────────────┐
        │                         │            │  │                  │
   ┌────┴─────────┐        ┌──────┴─────┐      │  │           ┌──────┴──────┐
   │ 主事件记录    │        │ NPC 发言   │      │  │           │   主对话     │
   │ (flash)      │        │ (另一模型)  │      │  │           │   (pro)     │
   │ sendRequest  │        │ sendRequest │      │  │           │ ST 当前连接 │
   └──────────────┘        └────────────┘      │  │           └─────────────┘
        ▲                        ▲             │  │                 ▲
        │ 喂：世界状态+最近消息    │ 喂：世界状态  │  │                 │ 注入：状态+事件记录+NPC发言
        └────────────────────────┴─────────────┘  └─────────────────┘
                 （从 context.chat 取最近 N 条消息拼进 prompt）
```

## 四、数据流设计（三条链路）

### 链路 A：主事件记录（轻量模型，价值最高）

**触发**：`context.eventSource.on(MESSAGE_RECEIVED)` —— 每轮主对话回复到达后。

**流程**：
1. 取最近 N 条消息（`context.chat` 尾部）+ 当前状态摘要（`buildSummary`）
2. 拼 prompt：「你是剧情记录员，根据以下对话，用 JSON 输出本回合发生的事件 `{summary, npcChanges, flags}`」
3. `resolveProfile(null, 'main_event')` → 拿 flash 的 profileId
4. `llmGenerate(profileId, prompt)` 生成
5. 解析 JSON → `POST /narrative/record` 写回后端（新增接口）
6. 后端存入 `state.narrative`（**新增字段**）

**产出**：主对话下一轮注入时，`narrative` 会出现在 prompt 里，pro 就知道「剧情进行到哪了」。

### 链路 B：NPC 意图 + 发言（另一模型）

**触发**：定时器（如每 30s）+ 后端 `GET /events` 消费。

**流程**：
1. 对每个活跃 NPC，拼 prompt：「你是角色 X，基于世界状态 + 最近对话，判断你要不要主动说话，输出 JSON `{intent:'talk'|'silent'}`」
2. `resolveProfile(npcRole, 'intent')` → 拿 NPC 模型 profileId
3. `llmGenerate(profileId, prompt)` 判定意图
4. `talk` → 再调一次生成发言 → 走现有 `POST /intent/record`（会 push `npc_speak` 事件）
5. 现有 `processNpcSpeakEvents` 消费事件 → 发言以系统消息发出

### 链路 C：主对话（pro，基本不动）

- 主对话仍走 ST「当前连接」= pro，不拦截
- 只需确保 `applyInjection` 注入的内容**包含** `narrative` + 最新 NPC 发言 + 状态摘要

## 八、风险与注意

1. **`sendRequest` 返回 `ExtractedData {content, reasoning}`**，取 `result.content`（已处理）。
2. **profileId 为 null 必须走 generateQuietPrompt 兜底**（已处理）。
3. **并发防抖**：链路 A 每轮触发，需防重复（`recordingInProgress` 锁，类似 `speakingInProgress`）。
4. **上下文长度**：拼最近消息要限制条数/字数，避免超 token。
5. **JSON 输出解析**：辅助模型可能不按 JSON 返回，需 `parseIntent` 式降级（关键词匹配）。
6. **主事件记录 vs 摘要的区别**：`buildSummary` 是确定性规则（时间/金钱），`narrative` 是 LLM 总结的剧情脉络，两者都要注入，但语义不同。

---

## 九、与「主对话本身切模型」的关系

用户本次需求**不要求**主对话在消息之间动态切换模型（那是拦截 `Generate` 引擎的大工程）。主对话固定 pro，轻量模型只负责「记录」和「NPC」两条辅助链路。若将来要主对话也切，另立文档。
